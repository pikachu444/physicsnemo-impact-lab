# Validation rollout 모듈의 실행 전 정적 검토

검토본: `plate_evaluation.py` SHA256 `6aa6ebd6329a1dbfc44fd68aa6f7743561ea2754321709c425c47dbd291e768b`, `selection_policy.py` SHA256 `a74d6626da4aa657344d06dd6823d6b1a9f5cc3eb76deb38cc0720e54bf42278`. 파일과 소스만 읽었으며 NumPy·Torch·프레임워크 import, 모델·GPU·평가 실행이나 새 fixture 생성은 하지 않았습니다. 학습 진입점은 동시 수정 중이므로 아래는 해당 두 모듈의 검토이며 최종 통합 승인과 구분합니다.

확인한 동작:

- 평가의 `37–61행`은 예측 위치를 다음 입력으로 사용하고, actuator/clamp만 알려진 다음 경계 위치로 지정합니다. 모든 단계의 plate 요소 역전과 최소 detF를 기록합니다. 기본 399단계에서는 399회 자기회귀이며 teacher forcing은 별도 선택입니다.
- `40–45,57–58행`은 비유한 출력·적분 위치를 실패로 처리합니다. `79–83행`은 음수 von Mises 출력을 잘라내지 않고 최소값과 개수를 남깁니다. `98행`은 변형률이 원 COMSOL 출력이 아닌 좌표 유도값임을 명시합니다.
- 평가 예외는 `132–138행`에서 `status=failed`, 단계·stage와 traceback 경로로 구분합니다. 정책의 `133–155,181–184행`은 미완료 결과, 비유한 상대 오차, 누락된 매 단계 역전 기록을 실패 후보로 취급합니다. 역전은 정확도 통과가 아닌 별도 invalid flag입니다.
- 정책은 두 validation 결과의 변위·응력 상대 L2 중 최댓값을 사전 규칙대로 사용합니다. 영변위/학습 평균 기준과 음수 응력은 진단으로 보존하며 정렬 기준을 몰래 바꾸지 않습니다. 이 순위는 제품 정확도 통과 판정이 아닙니다.

실행 전에 필요한 보완:

1. **실패 JSON 보존 경로:** 평가 `139–140행`의 `torch.cuda.empty_cache()`는 예외 처리 바깥입니다. CUDA context 오류 등으로 cleanup 자체가 실패하면 `142–143행`의 실패 JSON이 저장되지 않습니다. cleanup 오류를 별도로 기록하는 `try/except` 후 실패 JSON을 계속 저장해야 합니다.
2. **val-only 사전 경계는 호출자가 보장해야 합니다:** 평가 `20행`은 전달된 파일을 즉시 열고 `126행`은 이름/분할을 사전 검증하지 않습니다. 정책 `124–125행`도 결과 자신의 이름을 allowed 목록으로 사용하므로 고정 분할 계약 검사를 대신하지 않습니다. 통합부에서 파일 열기 전에 frozen validation 목록과 두 고정 진단 이름을 대조해야 합니다. `valid_9999` 같은 정규식상 validation 이름도 실제 허용 목록에서는 거부해야 합니다. 선택용 평가는 `rollout_steps==399`도 확인해야 합니다. 정책 자체는 양수 단계만 요구합니다(`135–138행`).
3. **기존 실패 기록 보존:** 평가 `135행`은 기존 traceback 파일을 덮어쓸 수 있고, metrics 파일의 배타적 생성 검사는 긴 평가 이후입니다. 새 출력 폴더/고유 prefix를 강제하는 통합 계약이 없다면 metrics·field·failure 파일을 평가 전 확인하고 traceback도 배타적으로 생성하는 것이 안전합니다.

첫 번째는 실패를 성공으로 오해하지 않도록 실제 저장 경로를 보호하기 위한 수정입니다. 두 번째와 세 번째는 호출부의 최종 구현에 따라 해결 여부가 달라지므로 통합이 끝난 뒤 다시 확인해야 합니다. 현재 기록을 val-only 전체 실행이나 새로운 최종평가 무접근의 실측 증거로 사용하면 안 됩니다.
